## 1. Requerimiento Funcional Evaluado

En el marco de la plataforma transaccional de oficios **ExpertoYa!**, se auditó el requerimiento **RF-04: Búsqueda y Recuperación Geolocalizada de Profesionales por Zona y Especialidad**.

El módulo permite a los clientes encontrar prestadores de servicios calificados combinando criterios geográficos (zonas de cobertura predefinidas o coordenadas) y categorías de oficios (gas, plomería, electricidad, entre otros). Técnicamente, el flujo involucra un cliente reactivo en **React 18** estilizado con **Tailwind CSS**, una capa de transporte REST provista por **PostgREST / Supabase Client**, y un motor relacional **PostgreSQL 15** configurado con índices optimizados y restricciones de integridad.

## 3. Justificación Técnica de los Puntajes Asignados

1. **Exactitud de Resultados (Nota: 4 / 5):**
   * *Justificación:* Las pruebas unitarias y de integración (CP-01 a CP-03 documentadas e ilustradas en las Figuras 2, 3 y 4 de **TP4-08**) demostraron que las cláusulas condicionales `AND` resuelven la intersección de conjuntos de datos de forma matemáticamente exacta en PostgreSQL. La búsqueda textual implementa el operador `ILIKE`, resolviendo adecuadamente las variaciones de mayúsculas y minúsculas. Se califica con 4 (y no 5) debido a que la base de datos carece de normalización de caracteres diacríticos mediante la extensión `unaccent`, lo que provoca que términos con tildes explícitas puedan omitir registros cargados sin tilde en nombres o especialidades.

2. **Combinación de Filtros y 0 Resultados (Nota: 4 / 5):**
   * *Justificación:* Al aplicar filtros excluyentes que devuelven un conjunto vacío (CP-04 y CP-05, Figuras 6 y 7 de **TP4-08**), el frontend no sufre anomalías de renderizado ni bucles infinitos de petición. El componente `EmptyState` ofrece una experiencia pulida, con redacción empática y un disparador que restablece los parámetros a su estado por defecto. Obtiene 4 puntos porque el sistema actualmente solo informa la ausencia de datos, sin sugerir de manera autónoma alternativas en localidades contiguas o términos ortográficamente cercanos.

3. **Tiempo de Respuesta Percibido (Nota: 4 / 5):**
   * *Justificación:* La latencia de red promedio se ubicó en **182.8 ms**, con un tiempo de renderizado percibido global de **285 ms**, valores sumamente competitivos para aplicaciones web (Figura 8 de **TP4-08**). El uso de índices compuestos `(activo, zona_id, especialidad_id)` asegura tiempos de escaneo en base de datos menores a 25 ms (Figuras 9 y 10 de **TP4-08**). La inclusión de *skeletons* visuales en Tailwind CSS amortigua la espera y previene cambios bruscos de diseño (*Cumulative Layout Shift* nulo). No alcanza los 5 puntos debido a que en condiciones de peor caso simulado (cold start de Supabase y red móvil inestable) la latencia trepó a 720 ms sin contar con una capa de caché local en memoria cliente (*SWR* o *React Query*).

4. **Claridad de los Mensajes de Error (Nota: 4 / 5):**
   * *Justificación:* Ningún error de infraestructura o código de estado HTTP 500 expone detalles sensibles, tablas o trazas de Supabase al usuario final. La arquitectura desacoplada canaliza las excepciones a través de notificaciones contextuales accesibles que cumplen las pautas WCAG 2.1 AA (doble codificación: color e icono vectorial, evidenciado en la Figura 11 de **TP4-08**). Se califica con 4 puesto que las opciones de recuperación son mayormente reactivas (mensaje informativo) sin diagnósticos interactivos más profundos para el usuario.

5. **Consistencia Frontend vs Supabase (Nota: 5 / 5):**
   * *Justificación:* Merece la calificación máxima (Excelente). Existe una sincronía perfecta y libre de mutaciones entre la estructura relacional de la base de datos (Figura 5 de **TP4-08**) y el modelo de datos en el cliente React. Las interfaces de datos garantizan que ningún campo requerido sea omitido o interpretado con tipos erróneos. Las relaciones foráneas `profesionales -> especialidades` y `profesionales -> zonas_cobertura` se resuelven limpiamente mediante joins automáticos de PostgREST, reflejando siempre información fidedigna.

6. **Recuperación ante Fallos de Red (Nota: 3 / 5):**
   * *Justificación:* Ante una desconexión intencional (modo *offline*, Figura 11 de **TP4-08**), la aplicación intercepta el error con un bloque `try/catch`, cancela peticiones pendientes mediante `AbortController` y habilita un botón para reintentar la acción. Sin embargo, se mantiene en nivel 3 (Bueno) debido a que no cuenta con un sistema de reintentos automatizados con algoritmo de retroceso exponencial (*Exponential Backoff*), ni reanuda la búsqueda de manera transparente al restablecerse la conectividad del dispositivo.

## 4. Conclusiones y Grado de Cumplimiento

El análisis de calidad sobre el requerimiento funcional **RF-04** concluye con un **Grado de Cumplimiento Muy Bueno (82.00% / Nivel 4)**. La plataforma *ExpertoYa!* dispone de una arquitectura robusta, estable y profesional, cuyo núcleo de búsqueda responde a las exigencias operativas de un producto listo para etapas de validación de mercado.

A los fines de avanzar hacia el **Nivel 5 (Excelente)**, se formulan dos propuestas de mejora técnicas y accionables:

### Propuesta de Mejora 1: Normalización Fonética y Diacrítica con `unaccent` y `pg_trgm` en PostgreSQL
* **Diagnóstico actual:** Las búsquedas con operadores `ILIKE` son sensibles a acentos y requieren coincidencias de subcadena exactas.
* **Solución técnica propuesta:** Habilitar en Supabase las extensiones nativas `unaccent` y `pg_trgm`:
  ```sql
  CREATE EXTENSION IF NOT EXISTS unaccent;
  CREATE EXTENSION IF NOT EXISTS pg_trgm;

  -- Función inmutable de desacentuado para indexación
  CREATE OR REPLACE FUNCTION f_unaccent(text)
    RETURNS text AS
  $func$
  SELECT public.unaccent('public.unaccent', $1)
  $func$ LANGUAGE sql IMMUTABLE;

  -- Índice para búsquedas difusas (fuzzy search) y tolerantes a erratas
  CREATE INDEX idx_profesionales_nombre_fuzzy 
  ON profesionales USING gin (f_unaccent(nombre_completo) gin_trgm_ops);
  ```
  Esto garantizará que búsquedas como `"tecnico"`, `"técnico"`, `"gasista"` o `"gazista"` recuperen los registros pertinentes, elevando la exactitud del resultado a nivel excelente.

### Propuesta de Mejora 2: Integración de TanStack Query con Estrategia Stale-While-Revalidate y Backoff Exponencial
* **Diagnóstico actual:** La comunicación con Supabase se ejecuta mediante hooks tradicionales con `useEffect`, dependiendo de un único intento de red y forzando peticiones repetitivas al servidor ante cada cambio de pantalla.
* **Solución técnica propuesta:** Integrar la librería **TanStack Query v5**:
  ```javascript
  const { data: professionals, isLoading, isError, refetch } = useQuery({
    queryKey: ['professionals', { zonaId, especialidadId }],
    queryFn: ({ signal }) => fetchProfessionals({ zonaId, especialidadId, signal }),
    staleTime: 1000 * 60 * 5, // 5 minutos de caché en memoria cliente
    retry: 3, // 3 reintentos automáticos ante fallo de transporte
    retryDelay: (attemptIndex) => Math.min(1000 * 2 ** attemptIndex, 30000), // Backoff exponencial
    refetchOnReconnect: true // Auto-recuperación cuando el navegador vuelve a tener red
  });
  ```
  Esta mejora resolverá las dos debilidades observadas en la auditoría: abatirá la latencia percibida a 0 ms para búsquedas frecuentes y elevará la resiliencia de red a nivel 5.

## 5. Limitaciones del Análisis de Calidad

Para contextualizar el alcance del presente informe y sus conclusiones, se reconocen las siguientes limitaciones metodológicas:

1. **Entorno de Ejecución Local y Conectividad Controlada:** Las mediciones fueron realizadas en entornos de desarrollo y emulación local de red en Chrome DevTools. No se efectuaron pruebas bajo condiciones extremas de latencia de torres móviles rurales o redes 3G/4G congestionadas de alta fluctuación.
2. **Volumen de Datos del Conjunto de Pruebas:** La base de datos de desarrollo cuenta con un dataset representativo pero reducido (~150 profesionales y 15 zonas geográficas). En consecuencia, los tiempos de ejecución de las sentencias SQL reflejan un costo de cómputo mínimo; un escenario de producción con más de 50.000 prestadores requerirá auditorías complementarias de particionamiento de tablas y consultas espaciales nativas con **PostGIS** (`ST_DWithin`).
3. **Ausencia de Concurrencia Simultánea y Estrés:** Los ensayos no contemplaron pruebas de carga masiva (*stress testing*) mediante herramientas como k6 o Apache JMeter, por lo que el comportamiento del *pool* de conexiones de Supabase frente a cientos de peticiones simultáneas no fue objeto de este ticket.
